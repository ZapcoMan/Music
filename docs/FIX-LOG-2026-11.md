## 二、行为变更（需要回归验证）

1. **鉴权从"可选"变为强制**。无 Token 的业务接口现在返回 401。免登录接口在 `WebMvcConfig` 显式白名单：登录、注册、静态资源（`/img/**`、`/song/**`、`/userImages/**`）、OpenAPI、`/actuator/health`、`/error`。
2. **角色隔离生效**。新增 `@RequireUserType`：`allCollect`、`consumer/delete`、`consumer/allConsumer` 仅管理员可用。admin 与 consumer 共用同一签名密钥，此前消费者令牌可直接调管理接口。
3. **身份改从令牌取**。`collect` 的 add/delete/collectOfUserId、`search-history` 全部 5 个接口、`consumer/update` 不再接受客户端传入的 userId。此前任何人可凭他人 userId 增删收藏、改他人资料。
4. **删除接口改为 DELETE**。7 处 `GET /xxx/delete` 改为 `@DeleteMapping`，前端两端调用已同批改为 `del()`。
5. **`R.error` 现在会设置 `success=false`**。此前失败响应里 `success` 是 `null`，前端 `res.success === true` 永远为假。
6. **新增登出接口** `POST /consumer/logout`、`POST /admin/logout`，把令牌写入 `jwt:blacklist:`，TTL 与令牌剩余有效期对齐。此前黑名单只读不写，"主动登出"不存在。
7. **上传集中校验**。六处上传统一到 `FileStorageService`：扩展名白名单（图片 5 类 ≤10MB、音频 6 类 ≤100MB）、服务端生成文件名（不再使用客户端原名）、目录创建失败显式报错。multipart 上限从 1024MB 收紧为 100MB/200MB。
8. **算法参数改为配置驱动**。前缀 `recommendation`（权重、量纲上界、FM 系数、新歌分档）。代码内常量退化为默认值。
9. **限流计数原子化**。原 `get → 判空 → set(1)` 在并发下会被直接绕过，现用 `INCR` + 首次设过期。
10. **CORS 单一出处**。`WebMvcConfig` 中的重复定义已删除，只由 `SecurityConfig` 提供，且改为精确来源白名单（`allowCredentials` 下不允许通配）。

## 三、算法与数据口径纠正（此前认知有误的部分）

- **六路召回的真实权重**：`collaborative_filtering 0.40`、`content_based 0.25`、`personalized 0.20`、`tag_based 0.20`、`search_history 0.20`、`popular 0.15`。`RECALL_AND_SEARCH_HISTORY_FEATURE.md` 里写的 0.25/0.25/0.15/0.15/0.2/0.2 与实际不符。
- **内容与个性化召回曾长期返回 0 首**：`getCollectByUserID` 未查询 `singer_id`，而这两路靠它取偏好歌手。现已补列并按收藏时间倒序。
- **CF 相似度此前只召回 ID 更大的用户**（`r1.consumer_id < r2.consumer_id`）。实测 ID 最大的用户旧版召回 0 人、新版 12 人。相似度粒度是**歌单**评分，不是歌曲评分——若要歌曲粒度需另行改造。
- **评分特征此前无区分度**：`ranks.score` 是 1–10 分制（实测某用户均值 6.0、无评分歌曲均值 6.9），而打分按 `normalize(x,0,5)` 并裁剪上界，导致 score≥5 全部饱和到 1.0；兜底值 4.0 是按 5 分制写就的，使无评分用户分数低于有评分用户（方向反了）。现量纲改 10、兜底改中性 5.0，并新增 `ratingCount` 置信特征。
- **新歌扶持此前做了两遍且破坏概率语义**：sigmoid 之后乘 1.5/1.3/1.1，同时线性项又有 `songAgeDays` 负权重。现改为 sigmoid 之前的加性增益；`createTime` 缺失在两层的相反判定也已统一为"年龄未知，不扶持不惩罚"。
- **融合层的"最佳策略"此前取决于 Spring bean 注册顺序**。现按"权重降序 + 名称字典序"固定遍历顺序，并按 `rank/recallSize` 归一化位置判定。
- **推荐缓存此前从未成功命中过**：直接缓存 `List<Song>` 时 Jackson 数组式类型标记只给元素写类型 ID、外层集合没有，读取必抛 `SerializationException`。现用 `CacheEntry` 包装，并对历史坏数据自动删除重建。
- **标签系统实际不可用**：`tag` 字典有 20 条，但 `song_tag` / `singer_tag` 为 **0 行**——V3 的自动迁移按 `song.introduction LIKE 标签名` 生成，而 `introduction` 存的是专辑名（"叶惠美""光年之外""Xposed"），5 个风格标签命中数全为 0。这是数据来源缺口，不是 SQL 缺陷；V3 也从未为 `singer_tag` 写过任何数据生成语句。
- **V2 迁移曾使 Flyway 链断裂**：`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 是 MariaDB 语法，MySQL 报 1064，导致 V2 之后全部迁移未执行。后果是 `search_history`/`tag`/`song_tag`/`singer_tag` 四表在 `db_music` 中原本都不存在，`song.tags`/`singer.tags` 列也不存在——而 mapper 的 `Base_Column_List` 含 `tags`，这解释了为何大量查询被迫改用 `Blob_Column_List`。

## 五、已发现但**尚未**解决的问题

1. **测试套件不可信且不可用**。`UNIT_TEST_REPORT.md` 声称"3 个测试类 31 用例"，实际 18 类 141 用例；16 个用例是空方法体（注释写"跳过"但不是 `@Disabled`，仍计为通过）；48 个 Controller 用例只断言 HTTP 200，而本项目业务失败也返回 200。更要紧的是**每个 `@SpringBootTest` 类都要独立启动 41 秒上下文**，全量跑不完，README 的 `Tests 141 passed` 徽章没有依据。
2. **H2 测试 schema 落后于实体**：`schema.sql` 无 `song.tags`、也无 `tag/song_tag/operation_log/search_history` 表，因此走 `Base_Column_List` 的新查询在测试库必然失败。
3. **删除歌手的级联语义待决策**：`song.singer_id` 无外键，删歌手会留下孤儿歌曲。删歌手是否连带删歌属于产品决策，本轮未擅自实现。
4. **`song_tag` 数据来源缺口**：需要后台标签管理或人工/AI 标注流程，`TAG_SYSTEM_OPTIMIZATION.md` 的方案基本停留在文档；`TagMapper.xml` 中 `batchInsertIgnore`、`selectHotTags`、`deleteSongTags` 等仍无 Java 调用方。
5. **`getByUsername` 等仍有调用**，但登录接口实际返回 `HashMap` 而非 `ConsumerLoginVo`；散参接口应接线 DTO（本轮删除的是零引用 DTO，未新增接线工作）。
6. **前端 vue-cli 老工具链构建未验证**：本轮前端改动只做了 acorn 语法解析与一致性核对，浏览器实测与 `npm run build` 未执行。
7. **字符集**：相关表使用 `utf8`（MySQL 8 中为 UTF8MB3 别名，迁移时已有 3719 警告），改 UTF8MB4 属独立变更。
8. **`selectSongsByTagIds` 等接口返回体的 `match_count` 字段无对应属性**，目前被忽略；若需要可解释性输出需扩 VO。
9. **README 的 API 返回码示例已在本轮修正为 20000/20001**，但 `API 开发文档.md` 中仍可能存在与代码不同步的字段说明，需逐接口复核。

### 补充：复查后确认仍未处理的问题

首版第五节列得不全，容易让读者高估完成度。以下按实测数据补记：

10. **`docker-compose.yml` / `docker-compose.prod.yml` 仍是明文口令并把数据库暴露到宿主机**：
    `MYSQL_ROOT_PASSWORD: root`、`SPRING_DATA_REDIS_PASSWORD: admin`，且映射 `"3306:3306"`、`"6379:6379"`。
    本轮只收紧了 `application-*.yml`，compose 这一层完全没动 —— 这是当前最高的残余风险。
11. **`Consumer.password` 没有 `@JsonIgnore`**（实测该注解在实体中出现 0 次）。
    含密码哈希的对象被整体写入 Redis 并原样返回给 `/consumer/selectByPrimaryKey`、
    `/consumer/login` 等接口，属于凭据外泄面。
12. **`/consumer/selectByPrimaryKey?id=` 越权未修**。
    本轮第 19 簇把它推迟到"契约治理"，但后续的 #23/#50 都未覆盖，属于遗留缺口
    （返回体从裸 `Consumer` 改为 `R<Consumer>` 会破坏前端读取，需与前端同批）。
13. **`RedisConfig` 仍使用 `activateDefaultTyping(LaissezFaireSubTypeValidator)`**。
    本轮只是绕开了它对根集合的坑（CacheEntry 包装），多态反序列化的攻击面本身未消除。
14. **缓存 key 前缀仍有 8 处字面量**（`"music:`）。本轮只把推荐缓存收敛到
    `RecommendationCache`，歌曲/收藏/评论/歌单/用户五个域仍是各自硬编码。
15. **`expiresIn: 86400` 与 `jwt.expiration` 是两个来源**（2 处硬编码）。
    调整令牌有效期配置后，前端拿到的过期时间不会跟着变。
16. **审计链仍未接线**：`OperationLogServiceImpl` 129 行、5 个近似重复方法，
    全项目注入点实测为 0。
17. **限流覆盖面仍只有 2 个登录接口**，与文档声称的"查询/提交/敏感操作全覆盖"不符。
18. **请求/响应日志拦截器的请求体恒为空**（内容包装器创建后未回挂到链路），
    审计日志实际拿不到 body。
19. **列表类接口仍无 LIMIT 且整表写入 Redis**（`allComment` / `allCollect` / `allSongList`）；
    分页查询复用非分页方法，会把 `lyric` 等大字段一起取出。
20. **分层越界未清理**：`AdminController` 仍直接注入 `AdminMapper`，绕过 `AdminService`。
21. **前端结构性问题未动**：两端 `api/http.js` 仍是两份近似拷贝、
    `Home.vue` 四段重复 catch、`Comment.vue` 从 unpkg 远程引 CSS 与本地版本不一致、
    管理端 router 无导航守卫、`useEslint:false`、
    axios 0.18 / webpack 3 / babel 6 / `node:16-alpine` 等过时且部分已 EOL 的依赖。
22. **`song.tags`（逗号串）与 `song_tag`（结构化表）双轨并存且无同步代码**。
23. 有意不做的两项：`R.error` 批量替换为 `throw BusinessException`
    （全局异常处理已覆盖，改写无收益）；删除歌手是否连带删除其歌曲
    （产品语义决策，需业务确认）。
